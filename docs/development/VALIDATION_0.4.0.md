## 关键验证与修正

- 更名为 GTNH: Handy & Nimble 后使用 `gtnh-hn` 发行前缀。新增 3 项更新器测试，覆盖新旧文件名、同版本优先新文件名、损坏新文件回退、错误仓库／文件名拒绝与 GTNH 精确匹配。`run-hn-rename-01` 再次通过 19 组多输出检查及四模块注册、显示名、父子关系和终端图标检查。配置、数据目录与注册 ID 未更改。

- 优化器输出开关新增 7 组后台检查：新放置与缺省旧 NBT 默认开启；服务端 GUI 动作、观察者同步、完整 NBT 往返、距离与非法动作拒绝；两个独立网络分别启停。原生／二合一的物品和流体通道在 40k/16k 超额缓存下关闭保护，逐一测试直接接收、配方输出事务、严格／普通预检查，确认后续产出拒绝且原库存不变。严格模式下超额首仓不再扣减空闲后仓的接收能力。关闭后每通道 160k 旧缓存全部输出一次，与已有 80k 合计 240k；重新开启无需重载即可恢复保护。设置不改变原有详细报告与重命名开关。夹具路径 `run-output-switch-01`。

- 进阶发信器使用石英纤维隔离的子网，与主网库存分开统计。子网从有物品、有流体到完全清空时，红石由 0 恢复 15；拆装带库存的元件也会更新。计数探针验证两个订阅者、1000 次空闲刷新共享一次初始枚举；普通库存差量不重扫全库，强制失效才重建。
- 原生 ME 物品／流体输出分别设为 16,000 缓冲。没有优化器时，已满缓冲拒绝后续 tick 的完成产出；有优化器时，四次 10,000 产出保留为 40,000，后续配方预检查仍拒绝启动。刷新后库存数量守恒，缓存保存至原生 NBT。
- 二合一输入在真实 GT 控制器的配方取料流程中同时提供物品和流体，精确扣除 7 个钻石与 123 mB 水。测试覆盖进阶自动选入两种通道、配置复制、清空配置、导入普通输入总线配置，以及服务端容器开启、同步和手动槽拖动。
- 修正 AE 库存迭代器的使用：其 `hasNext()` 会推进位置，重复探测会跳过条目。现在分别收集至多 16 个候选，再交替选择物品和流体。
- 智能阻挡夹具使用真实 AE2FC 接口与高级阻挡卡，接收网挂载三个 Forge `FluidTank(16000)` 的测试存储提供者。保留原生逐套正常、过大批次第一种流体占满三罐的复现。现在按用户要求移除强制等空保护，改由发送接口的限制批量发配卡控制单批上限。真实 AE CPU 在 8k mB 上限下，严格阻挡一次发送 8 套后等空；智能阻挡连续发送两批 8 套，库存守恒，每批只扣除一步。测试提供者不代表所有第三方接收设备。
- 批量限额由提交订单的网络决定是否启用，再读取各发送接口自己的卡与上限；事务结束恢复上下文，不会因借用样板而启用其他网络的优化。原生回退分支也检查实际投料，避免低于一套的上限被绕过。
- GTNH 2.9.1 的压缩聚变默认批处理会在 64 EU/t 下多取原料并延长时间。测试分别关闭批处理验证功率并行上限，再恢复原生设置验证输出和总能耗，保留原生行为。
- 适配 AE 记忆卡保存样板方法新增的玩家参数；保持集成样板复制测试通过。

## 边界

客户端动画、声音、NEI 拖入和最终界面外观没有启动客户端验收。服务端容器和相关处理流程已测试，客户端代码通过编译及检查。场景最长边从 192 提高到默认 1024，不能据此保证显卡帧率；快照仍为 200 tick，场景数据范围仍为 16 格，多门仍分别渲染。

二合一输入覆盖 GT 通用多方块输入收集。直接读取专用仓室列表、要求固定流体仓位置的特殊机器不在兼容承诺内。新增机器 ID 默认 31990、31991，在目标包内验证无冲突。

二合一 ME 输出总线已实现（默认 GT ID 31992）。同一个 AE 节点承载原生物品缓存与原生流体缓存提供者；物品使用原生输出事务，流体事务按同版本 GT 实现适配。共用一个升级元件槽，按元件所属通道作用，不同时升级另一通道。

### 二合一输出与超额缓冲补充验证

[双通道原始记录](https://github.com/arturia-Xayah/gtnh-hn/blob/3c213a59158884a5363172369b4d8aefca942a06/verification/0.4.0/mixed_output/mixed-output-tests.json)。使用 GTNH 2.9.1 后台服务端，含 8 组检查；并非启动客户端验证界面外观。

- 原生 StructureLib 位置校验：仅总线／仅仓室均拒绝，同一格同时声明两类输出才接受；支持原生 OR 与不改变添加器的别名。不将同一机器其他位置的权限合并；未知自定义添加器保守拒绝。自动搭建的材料筛选也拒绝单类位置，避免投影仪误放；额外拦截控制器直接收集总线的旧入口和成型后的异常列表。
- 实际构造大型化学反应釜，成型后经控制器的原生输出流程保存 13 个金锭和 123 mB 岩浆。
- 物品／流体通道各设 16,000 容量：四次不同 tick 的 10,000 产物各保存为 40,000，后续配方预检查拒绝，缓存 NBT 往返保持数量；输出到 AE 后累计数量守恒。移除优化器不删除剩余缓存。
- 双通道过滤、容量隔离、模拟不修改缓存、流体缓存向 AE 暴露、共用单节点及服务端 MUI2 界面构建通过。
- 严格容量检查修复：超额缓存的剩余空间可能为负，原生事务会尝试插入负数量并增加待输出堆叠。严格预检查将负接收量钳制为零，也覆盖关闭保护后留下的超额缓存；额外接收保护仍由输出设备网络中的优化器开关控制。独立物品／流体输出以及二合一输出均有回归覆盖。

### 多输出端回归与修复

[修复前复现](https://github.com/arturia-Xayah/gtnh-hn/blob/3c213a59158884a5363172369b4d8aefca942a06/verification/0.4.0/multi_output/before.json)；[修复后检查](https://github.com/arturia-Xayah/gtnh-hn/blob/3c213a59158884a5363172369b4d8aefca942a06/verification/0.4.0/multi_output/multi-output-tests.json)。独立的 GTNH 2.9.1 服务端，实际 AE 网络、GT 原生 ItemEjectionHelper / FluidEjectionHelper、原生及二合一输出端。

| 两个 16k 输出端，四次各 10k 完成产出 | 修复前 | 修复后 |
| --- | --- | --- |
| 两个物品缓存 | 40k / 0 | 20k / 20k |
| 两个流体缓存 | 40k / 0 | 20k / 20k |
| 下一份配方预检查 | 仍允许 | 正确拒绝 |

旧逻辑始终允许首个优化器端接收，使后面的空缓存一直未使用；新配方仍能通过后仓的容量预检查。这是分配与限产漏洞，复现场景中没有数量丢失。

修复保留 GT 的类型优先级和过滤规则：先按正常顺序尝试仍有空间的输出端，再把剩余产物交给符合过滤规则、所属网络有优化器的紧急接收端。两轮共享同一份原生事务，提交表没有添加副本，因此每个缓存只提交一次。配方预检查不使用紧急通道；无优化器的输出事务仍走原逻辑。单次配方超出剩余空间时仍保留 GT 原本的接收行为，不要求把每次完成产出精确均分。

12 组场景包含 200 组固定随机种子的配置组合，覆盖：多仓全满、部分满、原生与二合一混用、不同 AE 网络、无优化器、过滤与非过滤端混用、普通输出端、多个产物、模拟／未提交不改库存、严格容量检查、3,000,000,000 数量分段及逐端 NBT 恢复，以及移除／恢复目标存储后的数量守恒。

流体 NBT 边界单独记录：目标版本原生 `AEFluidStack.create(FluidStack)` 在进入输出事务之前就忽略自定义 `FluidStack.tag`，所以同一流体的这类标签差异会归并。带 NBT 的物品保持区分，不同注册流体保持区分；此回归按 AE 实际流体键核对数量，不声称修复了整个 AE 的流体 NBT 语义。

适用范围是 GT 通用事务输出流程。紧急缓存不替代机器自身的开工预检查，也没有在途产物预约账本。持续排放而不检查输出容量的特殊机器（例如原版大型锅炉的逐 tick 产汽），以及关闭产物保护的运行方式，不能据此保证缓存增长有界；自定义绕过通用输出分配的路径尚未逐台验证。

### 性能范围

- 优化器查询只遍历 AE 按类型索引出的优化器节点，合法网络通常只有一个；不枚举库存，也不扫描其他机器。真实 AE 网络热身后的 9 组微基准，每组 100,000 次查询，中位数约 30 ns/次；这只是单调用微基准，不是整服 MSPT，也不作为大型基地 TPS 保证。
- 二合一输出每 tick 处理两个原生提供者，工作量接近独立一总线加一仓，共用一个 AE 节点。缓存按物品／流体种类保存数量；40,000 不会生成 40,000 个条目。刷新复杂度主要受缓存类型数和 AE 接收设备影响。结构限制只在结构检测时判断，普通机器的流体输出查询在无已批准二合一端口时不额外遍历普通总线。
- 多输出端修复最多对给定的兼容输出端走两轮，不增加库存全网枚举；正常接收包装器每份事务建立一次并被多个产物复用，配方预检查及无优化器路径继续使用原迭代器。
- 进阶发信器共享按网络／通道统计，平时按差量更新；首次订阅或强制失效需要全量读取。原验证中的两个订阅者、1000 次空闲刷新只产生一次初始枚举。
- 二合一输入的定向读取按已有槽位查询；进阶自动选型会在设置的刷新周期遍历两类候选，够 16 槽即可停止。若库存类型很多且多数不满足最小量，仍可能遍历大量候选；过低刷新间隔会放大成本。
- 新卡使用 AE 缓存的升级数量，限额计算只遍历当前配方原料，不枚举全网库存；两项为零时跳过合计。两项设置以一个容器动作提交，服务端检查权限、距离、当前容器和卡片。重复超限日志至多每个接口每 200 tick 一次，防止多样板交替触发刷屏。接收端仍使用原生高级阻挡库存检查，其成本随子网库存和缓存刷新而变。限制单批可能增加实际发配次数；智能阻挡不额外等待清空。
- BC 预览仅显示一个范围线框，应用前不改变填充工作；穿门动画为短时特效。场景清晰度是更显著的 FPS／显存风险：同纵横比下最长边 192→1024 约为 28.4 倍像素；512 相比 1024 为四分之一像素。不能把这个比例当作 FPS 比例。
- 所有可见门仍独立渲染，默认每门最多 30 FPS。服务端场景采样半径仍为 16，实时间隔 5 tick、快照 200 tick；目的地采样共享并缓存，仅地形变化时重传地形。客户端每 tick 最多发出两个场景请求，多门轮流更新但不隐藏其他门。多目的地、多玩家同时观看仍会增加服务端采样和网络负担；这次提高分辨率不扩大服务端采样范围或频率。没有客户端 GPU/FPS 实测。


生产构建：`clean build prepareUpdateAsset`，不启用 `modernizationPackTests`，JAR 内不包含后台测试类。未推送 GitHub 或创建 Release。

## 限制批量发配卡实现边界

- 注册发生在 AE 升级枚举初始化阶段，先于枚举缓存和界面；不依赖 Java 25 下受限的 Forge `EnumHelper`，无需用户修改 lwjgl3ify 配置。
- 相同原料按 AE 的身份合计，物品包含 NBT；整除后取所有原料最小批数。原始总量和乘法受原有 CPU 范围检查约束，限额本身允许至 `Long.MAX_VALUE`，以除法计算避免乘法溢出。
- 本次仍未启动客户端。服务端实际容器及同步注册可验证；`≤` 按钮、输入框和弹窗的最终外观仅完成编译／目标方法核对，尚无实机视觉验收。卡片复用 AE 原生卡片图标并使用浅蓝色着色。
- 批量卡不是接收空间预约。原生部分接收会将余量保留在发送队列，修改上限不召回这些旧原料；智能阻挡也可能在同 tick 发多批。不要把每批上限当成子网总库存上限。
